# 需求完整性评审

## 输入与范围

以当前需求、明确范围、业务流程及用户指定参照材料为依据。先识别需求阶段和变更范围，避免把概念方案按详细设计的粒度机械判缺，也不把技术实现偏好当作业务必需项。

## 工作方法

1. 检查目标、使用角色、前置条件、输入输出、主要流程、异常分支和结束条件之间是否闭合。已有编号保留，临时定位编号不冒充正式编号。
2. 按任务相关性核对身份权限、数据范围、接口依赖、状态变化、并发重复、审计留存、性能容量和恢复要求；只评审受影响部分，引用已有共性规范避免重复建设。
3. 区分缺失、歧义、矛盾、不可验证和待决策项。每项问题说明具体位置、触发场景、实际影响和需补充的信息；“支持高并发”等表述需要可验证口径，但不擅自填入数值。
4. 将关键需求对应到可观察的验收条件，检查正常、异常和权限边界。建议明确范围与依赖，不把新增功能自动纳入已批准范围。

## 结果与复核

按用户需要提供评审结论、问题清单、待决策事项与验收口径建议。关注程度依据上线阻断或业务影响说明；未见实现或测试证据时不声称功能已完成。只要求评审时不额外生成完整实现方案或独立测试文件。

资料读取按 bank-document-qa，行文和文字审核按需使用 bank-document-writing、bank-document-review；要求文件交付时使用 bank-file-delivery。
